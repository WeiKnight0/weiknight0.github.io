# 进程间数据交付

## 传输层与网络层

网络层为不同主机之间提供逻辑通信功能，屏蔽了链路层及以下的异构性，协议运行在终端和路由器，提供 “尽力而为” 的服务，尽最大努力在终端间交付分组，但不提供任何承诺；传输层为**不同主机的应用进程**之间提供逻辑通信功能，屏蔽了网络层及以下的异构性，协议运行在终端而不是路由器，提供进程到进程的数据交付、差错检测等服务，还可提供可靠传输、流量控制、拥塞控制等增强服务。

## 端口号

端口号用 **16bit** 表示，允许有 65536 个不同的端口号，只有本地意义，分为三类：

- 知名端口：0-1023，全球通用端口号，由 IANA 负责分配；
- 登记端口：1024-49151，在 IANA 登记；
- 临时端口：49152-65535，通信结束后被系统收回。

# UDP

## UDP 的特点

无连接、不可靠；提供进程到进程的数据交付（复用和分解）、差错检测服务；无建立连接产生的延迟；不限制发送速率（不进行拥塞控制和流量控制）；报头开销小；协议处理简单。

## UDP 校验和

计算校验和时，要包括伪首部、UDP 首部和数据三个部分；包含伪首部信息是为了避免由于 IP 地址错误等造成的误投递；UDP 校验和的使用是可选的，若不计算校验和，该字段填入 0。

## UDP 的适用性

无建立连接产生的延迟；

不限制发送速率（不进行拥塞控制和流量控制），适用于流媒体应用、SNMP 等场景；

报头开销小；

协议处理简单，适用于 DHCP、DNS、SNMP 等应用。

# 可靠数据传输

## 可靠传输的条件

理想的传输条件为：传输信道不产生差错；不管发送方以多快的速度发送数据，接收方总是来得及处理收到的数据。实际网络都不具备理想传输条件，可能存在 bit 位差错、报文丢失、报文乱序、发送方与接收方速度不匹配等问题，因此必须使用一些可靠传输机制，在不可靠的传输信道实现可靠传输。

## RDT 1.0

RDT1.0 适用于基于完全可靠信道的传输，该信道没有 bit 位错误、不会丢失报文、不乱序且速度匹配。

- 发送方有限状态机动作：等待上层调用 rdt_send(data) ，收到调用后，将数据封装成报文（packet = make_pkt (data)），并通过不可靠信道发送（udt_send (packet)）；
- 接收方有限状态机动作：等待下层调用 rdt_rcv(packet) ，收到报文后，提取数据（extract (packet,data)），并交付给上层应用（deliver_data (data)）。

## RDT 2.0

- 发送方（2个状态）初始处于“等待上层调用”状态。当上层应用调用 **`rdt_send(data)`** 时，发送方首先执行 **`sndpkt = make_pkt(data, checksum)`**，将数据和用于差错检测的校验和封装成一个分组（`sndpkt`），然后通过 **`udt_send(sndpkt)`** 将该分组发送到不可靠的信道中。此时，发送方进入“等待 ACK 或 NAK”状态，暂停接收上层的新数据。当底层接收到反馈数据包触发 **`rdt_rcv(rcvpkt)`** 时，发送方会进行检查：如果 **`isNAK(rcvpkt)`** 为真，发送方再次调用 **`udt_send(sndpkt)`** 重传刚才的分组；如果 **`isACK(rcvpkt)`** 为真，说明发送成功，发送方不做任何操作（或执行空操作 `Λ`），直接返回初始状态，准备处理下一次数据发送。
- 接收方（1个状态）**始终**处于“等待下层调用”状态。当底层信道收到分组并触发 **`rdt_rcv(rcvpkt)`** 时，接收方首先检查分组完整性。如果 **`corrupt(rcvpkt)`** 为真（即校验和计算发现错误），接收方通过 **`udt_send(NAK)`** 将否定确认分组发回给发送方。反之，如果 **`notcorrupt(rcvpkt)`** 为真，接收方则执行 **`extract(rcvpkt, data)`** 从分组中取出数据，并通过 **`deliver_data(data)`** 将数据上交给应用层；紧接着，接收方通过 **`udt_send(ACK)`** 将肯定确认分组发回给发送方，以此告知对方数据已正确接收。

RDT2.0 存在的问题：如果 ACK/NAK 出错，发送方不知道接收方的情况，重传可能导致报文重复。

## RDT 2.1 与 RDT 2.2

- RDT2.1：处理出错的 ACK/NAK，发送方给每一个报文增加一个序号（sequence number），如果 ACK/NAK 出错，进行重传，接收方丢弃重复报文；
- RDT2.2：不使用 NAK，接收方发送上一次正确接收报文的 ACK 来替代 NAK，发送方收到重复的 ACK 等效于 NAK，重传当前报文（TCP 只使用 ACK）。

## RDT 3.0

RDT3.0 针对底层信道可能会丢包（data、ACKs）的问题进行了改进。采用了倒计数定时器（countdown timer）机制，如果在限定时间内没有收到 ACK，就重传报文；同时保留了校验和、序列号、ACKs、重传机制，序列号机制可以解决报文延迟导致的重复问题。

- 发送方：

  - **状态一：等待上层调用 0 (Wait for call 0 from above)**

    这是初始状态，发送方准备发送序列号为 `0` 的数据包。

    - **事件**：上层应用调用 **`rdt_send(data)`**。
    - **动作**：
      1. 调用 **`make_pkt(0, data, checksum)`**，将序列号 **0**、数据和校验和封装成一个分组 `sndpkt`。
      2. 调用 **`udt_send(sndpkt)`** 将分组发送到底层信道。
      3. **关键步骤**：调用 **`start_timer()`** 启动倒计数计时器。
    - **状态转移**：进入 **状态二（等待 ACK 0）**。

  - **状态二：等待 ACK 0 (Wait for ACK 0)**

    发送方已发出分组 `0`，正在等待确认。在此状态下可能发生三种情况：

    - **情况 A（收到正确 ACK）**：
      - **事件**：底层触发 **`rdt_rcv(rcvpkt)`**，且检查 **`notcorrupt(rcvpkt)`** 为真，同时 **`isACK(rcvpkt, 0)`** 也为真。
      - **动作**：调用 **`stop_timer()`** 停止计时器。
      - **状态转移**：进入 **状态三（等待上层调用 1）**。
    - **情况 B（收到错误 ACK 或数据损坏）**：
      - **事件**：底层触发 **`rdt_rcv(rcvpkt)`**，但 **`corrupt(rcvpkt)`** 为真，或者收到的是 **`isACK(rcvpkt, 1)`**（错误的确认号）。
      - **动作**：**无动作 (Λ)**。忽略该包，不停止计时器，继续等待。
      - **状态转移**：保持在 **状态二（等待 ACK 0）**。
    - **情况 C（超时）**：
      - **事件**：计时器触发 **`timeout`**。
      - **动作**：调用 **`udt_send(sndpkt)`** 重传刚才保存的分组 `0`，并再次调用 **`start_timer()`** 重启计时器。
      - **状态转移**：保持在 **状态二（等待 ACK 0）**。

  - **状态三：等待上层调用 1 (Wait for call 1 from above)**

    此时发送方已成功发送了分组 `0`，现在准备发送序列号为 `1` 的数据包。

    - **事件**：上层应用调用 **`rdt_send(data)`**。
    - **动作**：
      1. 调用 **`make_pkt(1, data, checksum)`**，注意这里序列号变成了 **1**。
      2. 调用 **`udt_send(sndpkt)`** 发送分组。
      3. 调用 **`start_timer()`** 启动计时器。
    - **状态转移**：进入 **状态四（等待 ACK 1）**。

  - **状态四：等待 ACK 1 (Wait for ACK 1)**

    发送方已发出分组 `1`，正在等待确认。逻辑与状态二对称：

    - **情况 A（收到正确 ACK）**：
      - **事件**：底层触发 **`rdt_rcv(rcvpkt)`**，且 **`notcorrupt(rcvpkt)`** 为真，同时 **`isACK(rcvpkt, 1)`** 也为真。
      - **动作**：调用 **`stop_timer()`** 停止计时器。
      - **状态转移**：回到 **状态一（等待上层调用 0）**，完成一个完整的周期。
    - **情况 B（收到错误 ACK 或数据损坏）**：
      - **事件**：底层触发 **`rdt_rcv(rcvpkt)`**，但 **`corrupt(rcvpkt)`** 为真，或者收到的是 **`isACK(rcvpkt, 0)`**（这是对上一个包的确认，属于过时的 ACK）。
      - **动作**：**无动作 (Λ)**。忽略该包，继续等待。
      - **状态转移**：保持在 **状态四（等待 ACK 1）**。
    - **情况 C（超时）**：
      - **事件**：计时器触发 **`timeout`**。
      - **动作**：调用 **`udt_send(sndpkt)`** 重传分组 `1`，并再次调用 **`start_timer()`**。
      - **状态转移**：保持在 **状态四（等待 ACK 1）**。

    RDT3.0的信道利用率很低

    信道利用率=(传输时延)/()=(数据/带宽)/(总时间)=(数据/带宽)/(往返时间+数据/带宽)

    $$
    U_{sender} = \frac{L/R}{RTT + L/R}
    $$

## 流水线、GBN 与 SR

流水线协议的优点是允许发送方发送多个报文而无需等待确认，提高了传输性能。

两种差错恢复方法：回退 N 步、选择重传。

回退 N 步和选择重传的区别如下：

- 发送方定时器设置：回退 N 步可只为最早发送但还未被确认的报文启动定时器；选择重传为每一个没有获得应答的报文设置定时器；
- 接收方处理失序报文：回退 N 步丢弃失序报文，对失序报文发送重复 ACK；选择重传缓存失序报文，对正确接收的报文逐一应答；
- 重传策略：回退 N 步当某已发送报文的定时器超时，将重传从该报文开始之后发送过的所有报文；选择重传仅重新发送没有收到 ACK 应答的报文；
- 缓冲区要求：回退 N 步发送方设置缓冲区以备重传，接收方不需要设置缓冲区；选择重传发送方和接收方都需要设置缓冲区。

# TCP

## TCP 的特点

面向连接；可靠的、按序的字节流；点对点、全双工通信；采用滑动窗口（流水线）、发送缓存、接收缓存、流量控制、拥塞控制、累积 ACKs 等机制；最大报文长度（MSS）在以太网中最大应用层数据 1460 字节。

## TCP 首部

TCP 报文格式主要包含源端口、目的端口、发送序号、确认序号、首部长度、保留、接收窗口、校验和、紧急数据指针、选项和填充、数据等字段，各字段作用如下：

- 源端口：标识发送方的应用进程；
- 目的端口：标识接收方的应用进程；
- **发送序号：该报文数据段首字节的字节流编号，初始序号可随机选择；**
- **确认序号：期望收到对方的下一个字节的序号，用于捎带应答、累计确认；**
- 首部长度：以 4 字节为单位，标识 TCP 首部的长度；
- **接收窗口：允许对方发送的字节数，用于流量控制；**
- 校验和：用于检测 TCP 报文段传输过程中的差错，强制使用；
- 紧急数据指针：指向紧急数据最后一个字节；
- 选项和填充：协商最大报文长度、窗口调节因子、时间戳等。

## TCP 选项

TCP 的可选项主要有最大段长度（MSS）、窗口比例因子、选择确认（SACK），各自作用如下：

- 最大段长度（MSS）：TCP 段中可以携带的最大数据字节数，建立连接时，每个主机可声明自己能够接受的 MSS，缺省为 536 字节；
- 窗口比例因子：建立连接时，双方可以协商一个窗口比例因子，实际接收窗口大小 = window size×2^window scale，扩大接收窗口范围；
- 选择确认（SACK）：允许接收端指出缺失的数据字节，改进了 TCP 的差错恢复机制。

## TCP 可靠传输

TCP 的基本可靠传输机制如下：

- 发送端：流水线发送数据、等待确认、超时重传，生成一个报文且定时器未运行时启动定时器，定时器超时重传报文后启动定时器（超时间隔 ×2），收到 ACK 报文后若仍有未被确认的报文则启动定时器；
- 接收端：进行差错检测，采用累积确认机制（推迟确认时间最多 500ms），对乱序处理协议没有明确规定，可选择不缓存（丢弃）或缓存（保留），常用缓存方式以提高效率。

## 超时重传

TCP 采用超时 / 重传机制处理报文丢失问题，且使用单一重传定时器（针对最早未被应答的报文）。具体机制如下：

①发送方生成一个报文且定时器未运行时，启动定时器；

②若定时器超时，发送方重传该最早未被确认的报文，并将超时间隔翻倍后重新启动定时器；

③若发送方收到 ACK 报文且仍有未被确认的报文，需重新启动定时器。超时间隔需大于连接的往返时间 RTT（可变），过短会导致过早超时和不必要重传，过长则对报文丢失响应缓慢。

为减少不必要的重传，TCP 做了优化：仅使用一个定时器避免超时设置过小的问题，利用流水式发送和累积确认避免因丢失 ACK 而重发报文；同时通过 RTT 估算（采用指数加权移动平均法计算 EstimatedRTT，结合 RTT 偏差 DevRTT 设置超时间隔 TimeoutInterval=EstimatedRTT+4×DevRTT）动态调整超时时间，初值为 1 秒，每超时一次超时间隔翻倍，减缓拥塞。

此外，TCP 还引入快速重传机制，当收到同一报文的 3 个重复 ACK 时，无需等待定时器超时，直接重发未被确认的序号最小的报文，弥补了仅靠超时重传恢复速度慢的不足。

## 快速重传

快速重传的触发条件是发送方收到了同一报文的 3 个重复 ACK。

动作是执行快速重传，重发未被确认的序号最小的报文，而无需等待定时器超时。

## TCP 与 GBN、SR

TCP 的差错恢复机制被看成是 GBN 和 SR 的混合体，原因如下：

- 定时器：与 GBN 类似，只对最早未确认的报文使用一个定时器；
- 超时重传：与 SR 类似，只重传缺失的报文；
- 接收方处理：接收方缓存失序的报文，对失序报文发送重复 ACK，采用累积确认，同时引入选择性确认（SACK）后可单独确认，结合了 GBN 和 SR 的接收方处理特点；
- 发送方重传策略：超时后仅重传最早未确认的报文，增加了快速重传，结合了 GBN 和 SR 的发送方重传特点。

TCP 在减小定时器开销和重传开销方面要优于 GBN 和 SR。

## 流量控制

TCP 流量控制的核心思想是接收方控制发送方，使发送方不因为发送数据太多、太快而导致接收方的缓冲区溢出。

具体措施：接收缓存中的可用空间称为接收窗口（rwnd），rwnd=RcvBuffer-[LastByteRcvd-LastByteRead]；接收方将 rwnd 放在 TCP 报头中，向发送方显式通告接收缓存的可用空间；发送方限制未确认的字节数不超过接收窗口的大小（LastByteSent-LastByteAcked ≤ rwnd）。当接收方的接收窗口为 0 时，发送方继续发送只有一个字节数据的报文（零窗口探测报文），以探测接收方窗口是否恢复可用。

## 三次握手

TCP 建立连接的 3 次握手流程如下：

- 客户端处于 LISTEN 状态，选择初始序号 x，发送 TCP SYN 报文（SYNbit=1，Seq=x），进入 SYNSENT 状态；
- 服务器处于 LISTEN 状态，收到 SYN 报文后，选择初始序号 y，发送 TCP SYNACK 报文（ACKbit=1；ACKnum=x+1，SYNbit=1，Seq=y），进入 SYN RCVD 状态；
- 客户端收到 SYNACK 报文后，发送 ACK 报文（ACKbit=1，ACKnum=y+1，SYNbit=0，Seq=x+1），进入 ESTAB 状态；服务器收到 ACK 报文后，进入 ESTAB 状态，连接建立完成。

不能用 2 次握手的原因：2 次握手可能导致半开连接、重复连接请求被错误处理等问题。例如，客户端发送的连接请求报文因网络延迟未及时到达服务器，客户端超时重传后建立连接并通信结束，此时延迟的连接请求报文到达服务器，服务器若采用 2 次握手会直接建立连接，但客户端已无连接意愿，导致半开连接；此外，还可能出现服务器接受重复的连接请求报文并发送确认，客户端收到后无法区分是新连接还是旧连接的确认，导致数据传输错误。

## 四次挥手

TCP 释放连接的 4 次握手流程如下：

- 客户端处于 ESTAB 状态，调用 clientSocket.close ()，不能再发送数据但可接收数据，发送 FIN 报文（FIN=1，seq=x），进入 FIN_WAIT_1 状态；
- 服务器处于 ESTAB 状态，收到 FIN 报文后，发送 ACK 报文（ACK=1；ACKnum=x+1），进入 CLOSE_WAIT 状态，客户端收到 ACK 报文后进入 FIN_WAIT_2 状态；
- 服务器数据发送完毕后，不能再发送数据，发送 FIN 报文（FIN=1，seq=y），进入 LAST_ACK 状态；
- 客户端收到 FIN 报文后，发送 ACK 报文（ACK=1；ACKnum=y+1），进入 TIMED_WAIT 状态，等待 2*max segment lifetime 后进入 CLOSED 状态；服务器收到 ACK 报文后进入 CLOSED 状态，连接释放完成。

# TCP 拥塞控制

## 网络拥塞

网络拥塞的产生原因：路由器出入端口速率不对称（入大出小）；网络流量汇聚，多入单出；路由器处理速率太慢；拥塞本身会进一步加剧拥塞。

网络拥塞的表现形式：延迟增大（路由器缓冲区中排队）；报文丢失（路由器的缓冲溢出）。

## 拥塞控制与流量控制

- 相同点：措施相似，都是通过控制发送方的发送速率来避免数据传输出现问题。
- 不同点：目标不同，流量控制的目标是使发送方的发送速率不超过接收方的处理能力；拥塞控制的目标是使发送方的发送速率不超过网络的处理能力。

## TCP 拥塞控制方法

TCP 拥塞控制的两种方法是网络辅助的拥塞控制和端到端拥塞控制，各自特点如下：

- 网络辅助的拥塞控制：路由器提供网络拥塞状态的显示反馈信息，可通过路由器直接反馈（阻塞分组）或经由接收方进行反馈（标识正常分组中的某个字段），例如 TCP ECN、ATM、DECbit protocols；
- 端到端拥塞控制：网络层没有为传输层拥塞控制提供显示支持，端系统自己通过观察分组丢包和时延等情况判断网络拥塞状态。

## 端到端拥塞控制

- 感知网络拥塞：发送方通过增加发送速率（发送窗口大小）探测可用带宽，收到 ACKs 表明无拥塞，产生丢包事件（超时 / 收到 3 个重复 ACK）表明产生拥塞；
- 限制发送速率：发送方使用拥塞窗口 cwnd 限制已发送未确认的数据量，LastByteSent-LastByteAcked ≤ cwnd，发送速率 rate = min (cwnd, rwnd)/RTT bytes/sec，cwnd 是动态的，随发送方感知的网络拥塞程度而变化；
- 调整发送速率：采用加性增乘性减（AIMD）策略，加性增指若无丢包，每经过一个 RTT 将 cwnd 增大一个 MSS，直到检测到丢包；乘性减指发送方检测到丢包后，将 cwnd 的大小减半（但不能小于一个 MSS）。

## 慢启动

慢启动的基本思想：在新建的 TCP 连接上，由于网络中的可用带宽未知，若直接以接收窗口大小限制发送速率，网络经常因为拥塞而崩溃，采用 “加性增” 增大发送窗口又太慢，因此慢启动在新建连接上指数增大 cwnd，直至检测到丢包（此时终止慢启动），希望迅速增大 cwnd 至可用的发送速度。

慢启动的具体实施：初始 cwnd=1 个 MSS，每收到一个 ACK 应答，cwnd 值 + 1，即每个 RTT，cwnd 值 ×2。

## 慢启动阈值与拥塞避免

慢启动阈值（ssthresh）的作用是防止拥塞窗口 cwnd 增长过大引起网络拥塞，取值为上次拥塞时 cwnd 的一半，是从慢启动转为拥塞避免的分水岭。

拥塞避免的实现方式：当 cwnd 低于 ssthresh 时，执行慢启动，cwnd 指数增加；当 cwnd 高于 ssthresh 时，执行拥塞避免，cwnd 线性增加（每个 RTT 增加 1 个 MSS），使网络不容易出现拥塞。

## 丢包后的处理

TCP 发生拥塞（丢包事件）后，根据丢包情况不同处理方式不同：

- 超时丢包：设置 ssthresh = cwnd/2，cwnd=1MSS，进入慢启动；
- 收到 3 个重复的 ACK 丢包：进行快速恢复，设置 ssthresh = cwnd/2，cwnd = ssthresh（TCP Reno 版本为 cwnd = ssthresh + 3），进入拥塞避免。

## 拥塞控制的公平性

TCP 拥塞控制的公平性目标是如果 k 个 TCP 连接共享带宽为 R 的瓶颈链路，每一个连接的平均传输速率为 R/k。

实际中影响公平性的因素：相互竞争的连接具有不同参数（RTT、MSS 等），不能保证公平性；应用（如 web）可以建立多条并行 TCP 连接，会占用更多带宽，不能保证公平性。
