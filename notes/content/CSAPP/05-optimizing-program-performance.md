优化的目标是在**保持程序正确**的前提下，减少完成任务所需的工作和时间。有效的优化通常来自三个方面：选对算法和数据结构；写出编译器能够安全优化的代码；在任务本身可拆分时利用并行计算。

编译器会做常量传播、公共子表达式消除、死代码删除、强度削弱和循环优化等变换，但它必须保留 C 程序定义的行为。指针别名、函数副作用、整数溢出规则和浮点数舍入都可能限制可用变换。因此，先理解正确性边界，再看生成的机器代码和测量结果。

# 1. 优化编译器的能力与局限

编译器能利用局部、明确的计算关系。例如：

- 把循环内不变的表达式移到循环外（代码外提）。
- 删除结果不会被使用的运算（死代码删除）。
- 把乘以常数改写为更合适的指令序列（强度削弱）。
- 在寄存器中保留临时值，避免重复读写内存。

编译器不能随意改变程序可观察的结果。下面的指针写入可能与先前读取访问同一位置，因此编译器不能在未证明不别名时简单地缓存旧值：

```c
void update(long *x, long *y) {
    *x = 1;
    *y = 2;
}
```

函数调用可能访问全局状态或通过指针修改内存；`volatile` 访问也有可观察副作用。这些因素会阻止某些代码外提或内存访问合并。`restrict` 可以向编译器承诺特定指针访问不别名，但只有调用方确实满足约束时才能使用。

优化编译器不能替程序员选择更好的算法，也不能推断不明确的业务约束。应先选择合适的复杂度和数据结构，再用优化选项编译，并查看实际汇编及测量值。不要依赖有符号溢出等未定义行为“帮助”优化。

# 2. 衡量程序性能

## 2.1 运行时间与加速比

用运行时间 $T$ 比较程序版本。若旧版本用时 $T_{old}$，新版本用时 $T_{new}$，加速比为：

$$
S=\frac{T_{old}}{T_{new}}
$$

$S>1$ 表示变快。比较时要固定输入、编译选项和运行环境，避免把系统负载、缓存状态或测量噪声误认为优化效果。

## 2.2 CPE

对于处理 $n$ 个元素的循环，可用每元素周期数（Cycles Per Element, CPE）衡量吞吐量：

$$
CPE=\frac{\text{运行周期数}}{n}
$$

在循环开销占主导且输入足够大时，CPE 有助于区分固定启动成本与每个元素的处理成本。它不是所有程序的唯一指标：小输入、I/O、内存分配和并发负载可能使单一 CPE 失去代表性。

可靠测量应使用多次运行，报告稳定统计量，并确认计时区间只覆盖目标工作。基准测试还要避免编译器把结果计算删除；让结果以可观察方式被使用。

# 3. 程序示例与性能上限

以对数组执行累积操作为例，基准实现通常包含循环控制、元素读取和累积运算：

```c
long sum(const long *a, size_t n) {
    long result = 0;
    for (size_t i = 0; i < n; i++) {
        result += a[i];
    }
    return result;
}
```

优化前先确认工作量和结果完全一致，再分析主要耗时来自哪里：循环分支、重复函数调用、内存访问、累积依赖链，还是处理器资源吞吐量。不同瓶颈需要不同手段；只缩短源代码不代表机器工作量减少。

若 $T_{old}$ 中只有比例 $p$ 的部分被加速 $s$ 倍，整体加速为 $1/((1-p)+p/s)$。因此，优化局部代码之前要估计它占总时间的比例。加速一个很少执行的函数，对整体运行时间影响有限。

# 4. 消除循环低效率

循环中不随迭代变化的计算可以移到循环外。例如，重复计算数组末尾地址、固定比例或不变的边界条件，可能造成不必要工作；编译器有时会自动外提，但应检查生成代码确认。

常见改进方向：

- 把重复的函数调用移出循环，前提是函数结果在循环内不变。
- 避免每轮重复计算相同地址或表达式。
- 让内存访问按连续地址进行，以利用空间局部性和缓存行。
- 消除不必要的条件测试，但不要改变边界行为。

循环简化必须保持对零长度、短数组和尾部元素的正确处理。边界条件错误会让性能提升变成正确性回归。

# 5. 减少过程调用

函数调用需要传递参数、保存必要状态并建立控制流连接。若小函数在热点循环中被反复调用，调用开销可能显著。编译器可以内联函数，把调用体直接放进调用处，继而进行常量传播和跨语句优化。

手动减少调用前应确认：

- 函数确实处于热点路径。
- 函数有副作用时，调用次数和顺序不会改变。
- 内联或合并不会过度增大代码，导致指令缓存压力或降低可维护性。

不应为了避免抽象而把所有函数都手动展开；优先让编译器优化并用测量验证。

# 6. 消除不必要的内存引用

若循环中的累计值每轮都写回内存、下轮再读回，机器可能无法把值长期保存在寄存器中。将临时值保留在局部变量或寄存器中，可以减少加载和存储；优化编译器通常会做寄存器分配，但别名或地址被取用可能限制它的判断。

内存访问优化需区分两类限制：

- **依赖延迟**：某次加载必须等前一次结果，关键路径被串行化。
- **内存吞吐量**：处理器或内存系统每周期能完成的加载/存储数量有限。

消除重复读写只有在程序语义允许时才成立。共享内存、`volatile`、I/O 映射地址和可观察副作用都可能要求保留访问。

# 7. 现代处理器与性能界限

现代处理器通过流水线和多个功能单元同时处理不同指令。它们可以乱序执行互不依赖的操作，但必须保证程序可见的结果符合架构要求。

性能常受两种不同界限约束：

- **延迟界限**：一条结果依赖前一条结果，构成循环携带依赖链。比如每次迭代都要用上一轮累加结果，处理器不能并行完成这些加法。
- **吞吐量界限**：指令彼此独立，但运算单元、加载/存储单元或内存带宽每周期能处理的工作有限。

若操作链的延迟为 $L$ 个周期，而每周期最多能启动 $C$ 个同类操作，那么长序列的吞吐能力同时受依赖延迟和功能单元容量限制。增加独立工作只能缓解延迟瓶颈，不能突破硬件吞吐上限。

条件分支还可能因预测失败清空流水线；但改用条件移动并非总更快，因为候选值可能都要计算，且某些计算无法安全地无条件执行。

# 8. 循环展开

循环展开让一次循环体处理多个元素，减少每元素的循环递增、边界判断和跳转开销。以每次处理两个元素为例：

```c
size_t i = 0;
for (; i + 1 < n; i += 2) {
    result += a[i] + a[i + 1];
}
for (; i < n; i++) {
    result += a[i];
}
```

第二个循环处理余数（尾部），保证奇数长度也正确。展开能降低循环控制成本，但若每次累加都依赖上次结果，关键路径仍然存在，性能提升可能很有限。

代码大小、寄存器压力和指令缓存也限制展开程度。展开因子过大可能增加寄存器溢出和前端取指成本，因此要以测量结果选择，而非一味增大。

# 9. 提高并行性

## 9.1 多路累积

把元素分到多个独立累加器，可打断单条循环携带依赖链：

```c
long s0 = 0;
long s1 = 0;
size_t i = 0;
for (; i + 1 < n; i += 2) {
    s0 += a[i];
    s1 += a[i + 1];
}
for (; i < n; i++) {
    s0 += a[i];
}
return s0 + s1;
```

两个累加链可交错执行，循环结束再合并。累积变量数量应匹配处理器资源；过多会造成寄存器压力。

重结合运算顺序必须符合语义。无符号加法按模运算具有结合性；有符号溢出在 C 中是未定义行为；浮点加法存在舍入且通常不满足结合律。若接口要求严格浮点结果，不能随意改变累加顺序。

## 9.2 SIMD 与数据级并行

SIMD（单指令多数据）指令可让一条向量指令同时对多个数据元素执行相同操作。循环迭代之间若相互独立、数据布局适合且没有别名或依赖障碍，编译器可能自动向量化。

帮助向量化的写法通常具有连续内存访问、明确的循环边界和无跨迭代依赖。对指针别名作出额外承诺（例如使用 `restrict`）前必须确认调用方满足承诺。

# 10. 合并优化及其限制

性能优化常需组合循环展开、多路累积和向量化。每种变换解决的问题不同：展开减少控制开销，多路累积降低依赖链限制，SIMD 增加数据级吞吐量。它们最终仍受功能单元、内存带宽、缓存和代码前端限制。

过度优化的代价包括：代码体积膨胀、寄存器溢出、分支预测变差、缓存局部性恶化、可维护性降低，以及编译器失去优化机会。每次变换后都应验证结果并重测。

# 11. 一些限制因素

- **寄存器数量有限**：同时存活的值过多会被写回栈，形成寄存器溢出（spill）。
- **指令吞吐量有限**：独立指令再多，也受功能单元每周期吞吐能力约束。
- **关键路径不可并行**：前一轮结果是后一轮输入时，简单展开不能消除依赖。
- **内存瓶颈**：缓存未命中或带宽不足时，算术优化可能不再影响总耗时。
- **代码大小**：展开和内联可能增加指令缓存压力。
- **正确性约束**：别名、溢出、浮点顺序和副作用限制可用变换。

# 12. 内存性能

处理器与主存的速度差距使得内存访问常成为瓶颈。缓存利用时间局部性（重复访问近期数据）和空间局部性（访问相邻地址）降低平均访问成本。

性能敏感的代码应关注：

- 连续访问通常比跨步访问更能利用缓存行。
- 多次重复使用的数据尽量保持在缓存或寄存器中。
- 工作集超出缓存时，数据布局和访问顺序会显著影响性能。
- 多线程共享同一缓存行还可能产生伪共享，即使它们修改的是不同变量。

改变内存布局可能比微调单条算术指令更有效，但要先确认瓶颈确实来自内存。可以通过硬件计数器或性能分析工具观察缓存未命中、加载/存储和周期等指标。

# 13. 性能优化技术

1. 选择合适的算法和数据结构，先减少渐进工作量。
2. 消除不必要的函数调用、条件测试、计算和内存引用。
3. 利用编译器优化，检查优化级别和实际机器代码。
4. 利用局部性安排数据访问。
5. 在迭代独立时使用循环展开、多路累积和 SIMD。
6. 对可拆分任务使用线程或多核并行，并考虑同步与通信成本。
7. 在关键路径和实际热点上花费优化精力，避免先优化不重要的代码。

# 14. 找出并消除性能瓶颈

先建立可重复的基准，再使用采样分析或硬件性能计数器定位热点和瓶颈。对热点函数进一步判断是计算延迟、指令吞吐、分支行为还是内存访问限制。

常用流程：

1. 固定输入和运行条件，记录基线时间及正确输出。
2. 使用 profiler 定位占时高的函数和代码路径。
3. 检查关键路径、循环依赖、内存访问模式和编译器生成代码。
4. 每次只做少量针对性改动，重新验证功能并测量多次。
5. 保留能稳定改善整体指标的改动，撤销无收益或增加复杂度的变换。

局部加速不一定带来整体加速。若某段只占总时间的比例 $p$，即使把它无限加速，整体加速上限也只有 $1/(1-p)$。性能分析应以实际应用总耗时为目标。

# 本章总结

- 正确性是优化前提；未定义行为不是合法的优化工具。
- 编译器能优化局部明确的计算，但别名和副作用会限制它。
- CPE、加速比和 profiler 帮助判断改动是否有效以及瓶颈在哪里。
- 循环展开降低控制开销，多路累积缓解依赖链，SIMD 提高数据级并行度。
- 现代处理器的延迟、吞吐量和内存层次共同决定性能上限。
- 以测量驱动优化，避免为不在热点中的代码增加复杂度。
